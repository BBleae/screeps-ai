## 结论与边界

同一 `db-storageab.json`（tick 504299）分叉，各推进 6000 tick。采样启动有 37–55 tick 差异，账本实际覆盖 5945/5963 tick；固定源码和对应版本的大脑，sample=25、probe-every=100。不是长期 RCL8 收益测量。

- 直接生效的 W33S7：CP **14.10 → 15.40/tick（+9.2%）**，收入 **45.39 → 44.82/tick**，CP/收入 **31.1% → 34.4%**。排除建造初期（tick ≥507000），CP **15.50 →16.53/tick**。
- 同一后段窗口的额外只读 CLI 采样：store link 均值 **526.9 →46.0**，满仓（≥790）采样 **43/120 →2/86**；候选 operator 累计送入 storage **4824**，观察到 `紫`、`紫甲` 两代，站位固定。原始追加记录为各运行目录 `hub-samples.jsonl`。
- 后段 hauler 源容器任务 **8.1% →0%**，投递 **12.7% →18.5%**。空闲 **78.6% →80.2%**，没有降低；低需求时待命是预期行为，不能把少空闲当成独立目标。不会为了增加活动而从 storage 取出再存回。
- W33S7 后段源容器均量 **60 →74**、掉落 **0 →0.46**，没有堆积；hauler 均数约 **1.75 →1.74**，保留目标底线 2，不为 operator 削减 hauler。
- 总 CP **62.16 →66.10/tick（+6.3%）**，但其它房间存在调度/发展分叉，不能把总收益都归因于本改动。W34S7 没建好 store link、没有 operator，其 CP 变化不作为本机制证据。RCL6 的 W31S6/W31S8 CP 分别下降，运输掉落没有一致恶化；这些房间没有启用新 hub 分支。无 link 的 W33S8、RCL5 的 W35S7 保持原运输规则。
- 全部 8 房没有运行错误、降级或丢房。单轮分叉不能保证其它房间 CP 完全一致，未声称每房都有性能收益。
