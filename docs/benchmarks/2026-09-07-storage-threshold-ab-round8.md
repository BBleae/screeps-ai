## 结论：弱通过，可以并入

按事先声明的口径（主指标 = 无外矿房的 CP 与 CP/收入；安全指标 = spawn 充盈、recovering / emergencyHarvest、storage 最低点；全账号 CP 只作参考）：

- **主指标**：W35S7 CP 8.6 → 9.1（+6%）、CP/收入 45% → 48%，storage 从"14–21k 之间摆动"变成"4–7k"，末态 12.9k → 5.2k。W33S8 完全持平（CP 14.1、CP/收入 74%）——它两组都没进 storageRich（末态 `on:false`），第 29.4k tick 才升到 RCL5、link 一座没建，阈值对它几乎不触发。两房收入都是自采 19.0–19.2/tick，跨组差 < 1%，所以这两个数字不含外矿噪声。
- **安全指标全过**：两组都 0 次 emergencyHarvest；recovering 采样 17/19/17 vs 20/18/16；hauler = 0 的采样 0/3/0 vs 0/4/0；spawn + extension 充盈度 W35S7 78% vs 78%、W33S8 72% vs 70%、W31S5 92% vs 87%；storage 最低点两组都触 0（不是 B 新造成的）。
- **全账号 CP 72.7 → 72.9**，在噪声内；采集 189.4 → 191.4、孵化 64.7 → 64.5。
- **机制与预期不同**：W35S7 在这两组里第 3.4–3.6k tick 就建成 2 座 link（含 ctrl link），所以是 **link 供能**，阈值实际开的是 `739a3a5` 的 storage → 控制器 link 通道，而不是 feeder（两组的 feeder 在岗都是 0）。证据：link 能量均值 466 → 755（+62%）、控制器容器均值 15 → 64。
- **幅度小于估计的 +11%，原因是运力**（peer 事先的判断成立）：W35S7 只有 2 只 hauler、投递占比 56% → 59%、控制器容器均值仍只有 64（容量 2000）。阈值把"能不能取"打开了，"取得多快"仍卡在 hauler。
- **W31S5 CP 2.7 → 1.7 不计入判决**：它两组都没进 storageRich（storage 开局 20k 一路花到 2k、`on:false`），阈值对它无效，差异是跑与跑之间的发散。

**建议**：并入 main。收益小但为正、无安全代价，且这一轮把测试里写死的 storage 数额一并参数化了。两个后续方向：(1) 基准里的 W35S7 是 link 供能，线上若是容器供能则走 feeder 路径，效果未必相同，值得用线上探针核对该房的 `plan.links.ctrl` 是否已建成；(2) 真正的天花板是运力——无外矿房的 hauler 编制没有把"storage → 控制器"的回流量算进去，或者让 feeder 也能在 link 供能房工作。

**线上复核（2026-09-07，部署版本 1788740125486）**：本文第 (1) 条提醒的差别成立——线上 W35S7 是 RCL4、**容器供能**（`plan.links.ctrl` 只在方案里，房里 0 个 link），所以线上走的是 **feeder 路径**，而基准世界里那间早已建成 ctrl link、走的是 storage → 控制器 link 通道。部署后线上 W35S7 立刻转富余（storage 15,428）并出 feeder 目标 1；W34S7（13,074）与 W33S7（11,216）也转富余但 feeder 目标 0（非容器供能，走本文测的那条通道）；W33S8（7,143 < 8,000）未开。也就是说线上同时吃到两条路径，其中 feeder 那条在分叉实验 7（`docs/benchmarks/2026-09-06-storage-ab-round3.md`）里对 W33S8 是 +94%，强于本轮基准的 +6%。
