# 监控漏检复盘与改进

## 证据与原因

1. 并非从未报警：旧logs/status.jsonl在2026-09-08 04:37、20:07、21:19及09-09 01:13、02:03多次记录W33S3空供能，01:13同时报告CP/tick降至4.61。此前没有持久事件状态、调查证据或恢复门槛，告警可能下一次消失，未形成可审计的处置闭环。
2. 最近18条成功采样包含数小时空窗（例如09-08 04:40→08:46→13:50、14:52→20:07），并非稳定每小时覆盖。这只能证明本地记录缺采样，不能据此断言调度器故障、额度耗尽或主机离线。当前任务已ACTIVE，下一轮显式检查90分钟采集空窗。
3. 外矿旧探针缺完整路径、掉落、真实在岗CLAIM、负载和能量账；旧规则仅比较矿工/reserver数量，连remoteHauler缺编都没有参与告警。“有人”不能证明到位/有效交付。已有需求函数本身如果算错，拿同一函数检查人数也可能一起漏检，新增独立结果检查补足此点。
4. 旧供能告警仅针对特定容器供能模式；升级回退混用版本，且有建设活动时可能被过滤。两端空容器曾错误描述为“持续为空”。这些会同时造成漏报和误报。
5. 自动化文字要求看净收益，但采集数据没有完整能量账。提示词没有让脚本具备那项测量能力；旧私服名字去重还漏计替补出生，需按修正账本验证，不能由交付增长推断盈利。

## 已实现

- schema4探针：creep真实ID/能量/CLAIM/控制器距离，当前可见预定覆盖旧情报、完整路径/缓存版本、地面资源ID与数量、满容器及局部预算计数。
- 独立结果检查：仓储积压与升级空载、WORK吞吐不足、同版本发展停滞与低利用、有效reserve交接、完整路线/道路矛盾、地面滞留与容器溢出。良好实测CP吞吐可解释空载端点；风险不等于已经证明bug。
- 同版本比较与至少30tick短窗端点；建设不自动掩盖升级回退。出生费用与收益覆盖明确为未知，绝不伪造精确年龄/衰减/利润。
- 持久事件账本：相同规则/房间归并，重复或紧急升级，采集失败和无视野不关闭；需同版本两个可比较正常样本才恢复，调查证据与下一步可追加。旧规则也进入闭环。
- 采集进程锁、每请求独立分片标识、失败退出2并留档；小时任务使用三次间隔60秒采样，强制阅读未解决事件并执行下一步。
