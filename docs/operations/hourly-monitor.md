# 每小时发展监控与处置

此流程用于线上发展、能量利用与外矿维护；不新增进攻、不改变现有进攻计划。监控本身是外部脚本，不需要上传游戏代码。

## 每轮必须完成

1. 读 CLAUDE.md 和存在的 AGENTS.md，检查 main、相关 worktree、上一轮事件账本与调查证据；通过活跃任务消息直接确认改动归属和唯一发布负责人。用户已删除旧协调日志，不读取、重建或写入 session-coord.md/json。主目录无关 WIP 不阻止独立干净 worktree 的调查、修复和测试；冲突编辑与部署必须协调串行，保留他人文件。
2. 在项目主目录运行 `python3 scripts/monitor.py --samples 3 --interval 60`。每次快照有随机请求标识，探针分片有独立名称，采集器有进程锁。成功采样写 logs/status.jsonl；退出1表示自上次心跳确认以来出现过新增事件（首次出现或解决/撤销后复发）、首次升级为 escalated 的事件或尚未附本次事件调查证据的 urgent 事件——告警累积在账本 `pendingAlerts` 里，launchd 每 30 分钟的 cron 采集用 `--no-ack` 只记账不确认，心跳这次运行成功结束时打印“待确认”清单并清空（采集失败退出2时不清，下次照样退出1）；退出0只表示自上次确认以来没有新情况，账本里长期未结的已知事件仍在（第3步照读）；退出2表示本轮未得到可靠结果。1和2均需处理，0也不等于“一切正常”。第一次无历史、采集失败、游戏tick未前进、缺视野，不能写“一切正常”。采样间隔是秒，判断窗口使用真实游戏tick。
3. **必须读 logs/monitor-incidents.json 中全部未解决项**，不是只读本轮控制台告警。同一问题按稳定规则/房间ID归并，三次不同tick复现或紧急条件升级处理。查看 investigation 的最近结论及 nextAction，完成下一步后补证据。自动恢复仅表示采样窗口恢复；已确认需要验证的效率调查继续按任务和分析报告跟进，直到有修复或不修改的证据结论，不能随瞬时报警消失而丢弃。
4. 对 urgent 立即核对现场：reserve已丢、预算越界、道路空路径却标记完成等。对三次复现的事件，本轮至少做一次有实质进展的诊断：读细分Memory/creep位置和负载、保存可复现快照、执行私服对照或分析已运行实验。不能再次只抄告警；资源被占时明确进程/世界/占用会话与下次执行条件，继续不冲突的调查。
5. 处理完写简短结果：采样tick/版本范围、监控空窗、异常或未知项、原因证据、采取动作、验证结果和下一步。缺少成本账时明确“净收益未知”，不能以角色齐全、无错误、地面减少或交付增加证明效率正常。

## 判定与诊断

- **发展与供能**：同版本、同RCL窗口看CP/tick；有工地也不能自动屏蔽发展停滞。并查升级WORK、空载比例、源/仓储缓存、Link和容器实际供能、采集WORK缺口。有效spawn能量预留期间暂缓供需错位规则，不视为旧事件恢复；队列超时及发展检查仍执行。WORK只是容量上界，编制变化、建设预算、搬运和boost要解释，风险提示本身不是修代码的证据。
- **reserve**：读当前可见控制器，旧情报扣除经过的tick；角色存在、正在孵化或在房间内不等于到位。检查CLAIM存活、控制器距离、TTL、实际队列/出生时间、在途疲劳与到位时刻。能量不足时同时检查合法小身体、满配攒钱时间，以及其他候选的实际身体成本和孵化占用；不得用容量上限代替实际身体。多个接班需求不能重复承诺同一笔能量或同一个孵化时段。监控的距离+12+60+20仅是接班下界，不能当作沼泽/堵路的精确ETA。无视野时保留未知，必要时从现有单位/情报补证据。
- **外矿运输**：检查完整路径与缓存版本、掉落目的地、全程道路、满容器、同ID地面堆积、单位负载和实际交付。重复出现的同ID可能期间补充或被部分拾取，不是精确资源年龄；两个端点不能计算精确衰减损失。
- **成本**：storageConsumerFallback、remoteEnergySalvaged、remoteRoadBudget只是局部计数，后者的delivered只覆盖花过修路预算的趟次。它们都不是完整能量账。先看 docs/analysis/2026-09-09-energy-supply.md、docs/benchmarks/2026-09-09-remote-route-ab.md；稳定期仍需固定源码/快照私服账本按真实creep ID核算孵化、运输交付、建设、道路/容器维修、必要防御，分清母房共享费用。禁止复用已撤回的名字去重现金结论。保存固定tick端点和账本版本；采样时才首次见到creep也可能漏掉生命周期，应连续记出生事件。
- **监控自身**：距上次成功采集超过90分钟记空窗，核对调度执行/主机可用性。本地监控无法在主机离线时自救；下次运行必须显式报告空窗，不能补写不存在的观测。已有证据不足以把历史长间隔直接归因为调度器故障。
- **建设停滞**：探针逐工地记录游戏当前 `siteWanted` 决策。明确因经济门槛暂停的工地显示“经济策略暂缓”；恢复后从新的有效窗口观察停滞。缺决策字段不自动屏蔽，跨源码版本不混算。此规则不屏蔽房间发展、仓储或供能的独立异常。

## 修复、验证和关闭

确认新bug可复现后，按 CLAUDE.md 最小修复：回归测试、游戏代码实际生效断言、完整私服和基线验证、独立原子提交、通过任务消息确认的唯一发布负责人、干净部署工作树、activeWorld预检、部署版本与模块匹配、上线新鲜复查。优化做同快照单变量A/B；不重跑挑绿，不因为一条风险提示就加人、停矿或回滚。回滚也要核对同版本可比较窗口和因果证据。

只改外部监控时，运行完整Python测试、`node test/monitor_probe_test.js`、Python语法及线上新鲜探针验证，不为了部署监控重新上传游戏模块。

规则没跑（检查崩溃、字段缺失、无视野、临时暂停）时事件保持 awaiting-evidence，沉默不是证据。唯一例外是范围已可证明不存在：外矿记录被删除、`enabled:false` 且 `suspendReason` 为 `notWhitelisted`/`tooFar`、或房间已不归我们（快照非空时）——这类事件记为 `obsolete`（不计入未结，`resolution.reason = scope-gone:*`），同一规则再次命中即按新事件重开；已标 `--requires-fix` 的缺陷不随范围消失出账，保持 awaiting-fix 并记 `scopeGone`。`monitor:economy-coverage` 是固定声明，记为 observing（info），不触发退出码。

事件自动恢复必须是规则实际再次检查过、同版本两个不同tick正常样本且至少相隔30ticks；没有视野/暂停/版本混杂不能用沉默证明修复。legacy旧规则至少需要同版本100tick比较窗口才能进入恢复。恢复状态只是观测条件消失；代码修复完成声明仍需上述测试/部署证据。一个未知项不能靠手改status或清空日志关闭。

补调查证据使用：

```sh
python3 scripts/monitor_health.py --incident '房间:规则' --note '证据支持的结论' --evidence docs/analysis/实际报告.md --next-action '明确下一步及触发条件'
```

确认源码缺陷后，给上述命令加 `--requires-fix`：即使预定/供能暂时恢复，也保留为awaiting-fix，不从待办消失。完成实际测试部署后，带真实验证报告及 `--verified-version <线上版本>`；工具要求5分钟内的同版本成功采集和至少相隔30tick的两个恢复样本才允许标记已验证。

该命令默认不强制关闭事件。完整能量账缺口会一直保留；每轮引用最新稳定期报告与下一步，不需要为这个固定未知项反复启动相同私服。优先处理有新增证据、紧急风险或尚未调查的事件。

## 长跑与并发

沿用自动化原有RCL8长跑观察要求：读当前 run.json/progress.jsonl、源码/大脑版本与进程；不杀、不重启其他会话实验，不混用长跑版本。可用实验先分析，缺必要证据再在资源允许时新建独立验证。每轮到点不代表可以抢占其他会话的发布职责；先直接沟通并确认交接。

### 本轮（W33S7 维修饥饿 + builder 编制）新增的规则与字段

探针每房新增（schema 仍是 4，纯增量）：

| 字段 | 含义 |
| --- | --- |
| `roads.{count,planCount,onPlan,offPlan,minHits,minOnPlanHits,minRatio,minOnPlanRatio}` | 方案内/外的道路数量与最低血量比例。**只看方案内**：方案外的旧路按规则任其衰减，不算故障 |
| `upgrade.{work,cap,duty,low,supply,storage}` | 控制器取能预算（`Memory.rooms[房].upgradeBudget`）：能量吃紧时 `work > cap` 且 `duty < 1` |
| `builderFeed.{wait,self}` | builder 等投递（wait）/ 本来会等但没人来、自己去取（self）的 tick 数 |
| `outOfReachRepair.{count,debt}` | 决策事件：塔射程外有维修债而放行 builder 编制的 tick |
| `outOfReachBelowFloor.{at,count,debt}` | 小额维修债低于孵化下限而延期的决策；必须与当前 state 的处数和债务匹配 |

新增告警（`analyze_room`）：

- **射程外有维修债却在岗 0 只 builder** → 告警；仅当 builder 目标为 0、30 tick 内的小额延期决策与当前债务及处数完全匹配、方案内道路均不低于 20% 时暂缓此条。旧决策、债务变化、已要求 builder 或危急道路都不能屏蔽告警。
- **builder 编制缺口**：`state.builderTarget > 0` 但在岗 0 只（孵化排队/能量不足）
- **方案内的路掉到 20% 危急线以下** → 告警（含射程外待修处数；这是"路在烂且没人修"的直接信号）
- **升级限流没生效**：`upgrade.work > cap` 但 `duty >= 1`；或能量吃紧且最近有竞争需求而 `cap` 为空

### 同 tick 孵化意图（2026-09-13）

引擎接受 `spawnCreep` 后，当前 tick 的 `spawn.spawning` 仍可能为空。空闲漏造告警先扣除 `spawnQueue.at == mon.t` 时的 `spawnQueue.spawned` 动作数；旧 tick 的动作不抵扣，多 spawn 剩余的真正空位仍参与告警。编制、采集 WORK 缺口继续记录，队列超时等独立规则不受影响。73661316 的 W33S3 实景回放复现并修正了这类误报。

### 升级者接班预算（2026-09-13）

`upgraderLeg` 记录接班旅行预算及完整性。检查实际孵化器位置、角色工作位、真实道路/障碍和满载疲劳；规划锚点不是实际出生位置，正在孵化或在途也不等于接班完成。诊断中用真实creep ID串联请求、出生、到位和正升级事件，避免把空载在途误判成Link断供。

供能错位仅统计控制器3格范围内的升级WORK，仍在步行的接班者不计入该需求。范围字段未知、非法或当前无人进入升级范围时，本条不提供健康覆盖；旧事件等待证据，发展停滞与路线规则继续独立判断。进入合法范围也不保证产生升级，结论还需实际CP增量或成功事件。

`upgrader-route` 仅在有升级WORK且预算遥测不超过300tick、`complete`为布尔时检查。`complete=false`或无效旅行时间需调查；`reason=lifetime`表示物理路线可能完整，但加上孵化后不能兑现生命周期内的交接预算。缺失、过期或未来遥测不构成恢复证据，CPU/房间发展/供能规则继续独立执行。

静态旅行估算不保证拥堵下的实际到位。新异常仍需还原同起点、同身体和逐tick轨迹；不要只扩大人数、提前量或关闭告警。测试固定地形也不等于固定场景：必须冻结实际spawn、对象、Memory及用户激活状态，播种完成先经过持久化屏障，再做可能失败的前提检查；保存失败种子，不能重随机挑绿。

升级限流的竞争事件必须不晚于预算采样：不能用较晚发生的竞争去证明较早的无限流决策错误。时间不匹配时保留未知，继续补对齐观测；在途WORK稀释限流预算的独立源码问题不能因此被屏蔽。
